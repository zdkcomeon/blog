全局规则文件（AGENTS.md）

日常 AI 编程协作使用的全局规则。

下载 AGENTS.md 原文件，可放在 Codex 全局配置目录中使用。

第一性原理

从第一性原理出发，克制改动范围、测试用例和验证步骤，只做确有必要的事。

编码规范

通用代码格式

  • 简单赋值和方法调用遵循 IntelliJ IDEA Java 格式，能保持单行时不要无意义换行。
  • 字段声明、注解成员、方法和逻辑代码块之间保留 IDEA 格式化所需的空行，不要为了紧凑删除必要空行。

Spring 依赖注入规范

  • Spring 管理的 @Controller、@RestController、@Service、@Component、@Configuration 等组件，其 Bean 依赖统一使用 @Resource 字段注入；不要为依赖声明 private final 字段，也不要编写仅用于依赖注入的构造器。
  • 使用与项目版本匹配的注解包：Spring Framework 6 / Spring Boot 3 及以上使用 jakarta.annotation.Resource，旧版本项目使用 javax.annotation.Resource。
  • 同一类型存在多个候选 Bean 时，使用 @Resource(name = "beanName") 明确指定 Bean，避免依赖字段名隐式匹配。
  • 普通配置值使用 @Value 或 @ConfigurationProperties，不使用 @Resource 注入字符串、数字、布尔值等配置项。
  • @Bean 方法参数、普通业务对象、实体和 DTO 的构造器不受本规则限制；这些构造器应按对象建模需要保留。
  • 修改已有 Spring 组件时，若发现构造器注入，应在本次改动范围内一并改为 @Resource 字段注入，并同步调整测试；不要为了测试便利在生产代码中保留或新增依赖注入构造器。

第三方交互日志

  • 新增或修改第三方 HTTP、RPC、SDK 等交互时，必须记录便于排查的调用日志：请求目标、脱敏后的入参/请求体、响应状态与响应体、耗时，以及异常上下文。
  • 请求与响应日志必须可关联到同一次调用；异常日志应同时包含目标、脱敏后的关键入参和耗时。
  • 严禁在日志中输出密码、token、Authorization、Cookie、完整 webhook 地址、密钥或其他凭据；URL、请求头和请求体中的敏感字段必须先脱敏。
  • 若通用 HTTP 工具无法安全地记录完整上下文，应在具体第三方网关或调用方记录专用日志，避免为排查方便而扩大其他调用的敏感信息暴露面。

日志可检索性

  • 新增或修改应用日志时，日志事件文本必须使用英文 ASCII，并采用稳定、可搜索的事件名，例如 similar_sku_attribute_analysis.prompt_assembled 或 order_sync.request_failed；不要将中文自然语言作为日志事件文本。
  • 日志事件名优先使用小写字母、数字、下划线和点号；同一业务流程的开始、成功、失败、重试等事件必须使用一致前缀，便于日志索引和聚合查询。
  • 面向接口调用方的错误消息、页面文案和业务数据不受本规则限制；它们可以按产品需要使用中文。

关键流程与异步任务日志

  • 新增或修改异步任务、批处理、数据同步、消息消费、缓存/分布式锁控制或其他关键业务流程时，必须为每个可独立排查的步骤记录明细日志；不能只在流程开始和最终异常时记录日志。
  • 日志至少覆盖：请求接收与参数解析、缓存查询与命中、锁获取/竞争、任务创建与提交、数据源加载、关键计算或提示词组装、第三方调用、响应解析与校验、数据库/缓存写入，以及成功、失败和重试分支。
  • 同一流程的日志必须可通过 taskId、requestId、traceId、业务主键或其他稳定关联标识串联；异步执行前后必须传递该关联标识。
  • 每个耗时步骤应记录开始与结束（或结束时的耗时）；查询、写入和批处理还应记录目标、关键筛选条件、记录数或受影响行数、结果状态。发生异常时须同时记录当前步骤、关联标识、关键上下文、耗时和异常堆栈。
  • 在不违反凭据保护要求的前提下，日志应保留足以复现问题的业务入参、数据加载结果、请求体和响应体；密码、token、Authorization、Cookie、密钥、完整 webhook 地址及其他凭据仍须严格脱敏。

API 入参与 MyBatis 规范

以下约定适用于使用请求 DTO、Jakarta Bean Validation 或 MyBatis 的项目；若仓库内存在更具体的规则，以更具体的规则为准。

  • 对排序字段、排序方向、TOP 档位等有限且稳定的取值集合，优先定义枚举，并让枚举负责参数值解析与合法性约束。不要在 Service 中重复维护 ALLOWED_*、DEFAULT_* 等字符串集合或常量列表。
  • 简单默认值直接定义在请求 DTO 字段上，例如页码、页大小和默认排序。不要在 Service 中为同一个默认值再写兜底分支；只有依赖运行时数据或业务上下文的默认值才由业务层计算。
  • 可声明的入参校验优先使用 @Valid、Jakarta Validation 注解和必要的类级约束完成。避免为必填、格式、范围、枚举值及起止区间等常规校验编写庞大的 validateAndNormalize 方法；Service 仅保留依赖数据库或跨对象状态的业务校验。
  • 查询型筛选条件原则上不因“该条件下查不到数据”而提前抛错；只要参数格式合法，就执行查询并返回成功空集合或空页。除非接口契约明确要求，不要为了确认筛选值存在而额外查询并强制终止请求。
  • 支持多选的筛选项直接使用数组或集合入参，并在 MyBatis 中通过 IN 与 foreach 查询；可选筛选项为空时不拼接对应条件。入参层完成必要的去空、去重和格式约束，避免 Service 中重复清洗。
  • 仅表达月份的字符串统一使用紧凑 yyyyMM 格式，例如 202511；不同时兼容多种月份格式，除非接口契约明确要求。
  • 新建或修改 MyBatis XML 查询时，为返回对象定义显式 resultMap，清楚维护列与 Java 字段映射；不要仅依赖 resultType、下划线转驼峰或 SQL 别名的隐式映射。

API 出入参注释

  • 新增或修改对外 HTTP 接口时，必须为请求 DTO、响应 DTO 及其嵌套 DTO 补充类注释和字段级注释，避免调用方只能从字段命名推测契约。
  • 请求字段注释至少说明业务含义、是否必填、格式或取值范围、单位/币种（适用时）以及默认或兼容行为；使用 @JsonAlias、枚举、数组或嵌套对象时，必须明确其 JSON 入参约定。
  • 响应字段注释至少说明业务含义、JSON 字段名、格式/单位，以及返回条件；状态、错误信息、异步任务结果、分页数据等条件字段必须清楚说明何时出现及可取值。
  • 可能超过 JavaScript 安全整数范围的标识类字段，除遵循字符串序列化规则外，注释中还应说明其以字符串返回的原因。
  • 接口实现、校验规则、序列化注解或返回语义发生变化时，必须同步更新对应 DTO 注释；内部纯持久化实体和不对外暴露的临时字段无需为满足本规则而补充接口注释。

API JSON 字段命名规范

  • 对外 HTTP 接口的 JSON 请求和响应字段统一使用小驼峰命名法，不直接暴露数据库的蛇形字段名。例如，数据库字段 review_time 在接口中返回为 reviewTime。
  • 接口字段名必须准确表达业务含义。数据库字段映射到接口对象时，应使用语义对应的小驼峰字段，不要为了复用已有字段而改成含义不同的名称，例如不要将评论时间 review_time 返回为 gmtCreate。
  • 数据库字段名、Java 字段名和 JSON 字段名不一致时，必须通过明确的映射或序列化配置完成转换，并同步更新响应 DTO 注释和接口文档。

数据库时间字段规范

  • 新增或修改数据库时间字段时，默认使用不带时区的时间语义：PostgreSQL/Hologres 使用 TIMESTAMP（不要使用 TIMESTAMPTZ），Java 实体使用 LocalDateTime。
  • 需要按业务时区生成、解析或在外部接口间传递时间时，在应用层显式转换；只有接口契约或既有表结构明确要求时，才使用带时区类型。

数据库主键与独立 ID 规范

  • 新建由应用维护的业务表，尤其是配置、权限和管理记录表，必须定义明确的主键，并保留独立的 id 字段；不要因为使用业务联合主键而省略独立 ID。外部既有表或有明确特殊约定的数据表，按其实际契约处理，不擅自改造已有结构。
  • 独立 ID 默认使用 BIGINT NOT NULL，由服务端沿用项目已有的唯一 ID 生成方式，例如雪花 ID；已有 UUID 等明确约定时遵循项目约定。新增记录时生成 ID，修改时保留 ID，删除后重新新增默认生成新 ID；独立记录 ID 不与用户 ID、站点 ID 等业务字段混用。
  • 主键设计必须同时考虑记录定位和业务唯一性。MySQL、PostgreSQL 等支持独立唯一约束的数据库，默认使用 PRIMARY KEY (id)，并为需要唯一的业务字段组合定义 UNIQUE 约束，避免仅靠新增前查询判断是否重复。
  • Hologres 不支持额外的 UNIQUE 约束；需要保证业务字段组合唯一时，使用该组合作为联合主键，同时保留独立 ID 用于接口定位，不将 ID 加入该联合主键而导致同一业务组合可以重复。分布键应按主要查询方式设置，并满足其必须属于主键列的要求。
  • 配置或管理记录的新增、修改和查询响应应返回独立 ID，修改和删除优先按独立 ID 定位；记录所属用户、站点等业务归属字段是否可更换，应在接口契约中明确。当联合主键用于业务唯一性时，修改和删除先按 ID 加载记录，再同时限定 ID 与业务主键执行写入，避免旧请求影响删除后重新创建的记录。
  • 数值型独立 ID 对外接收和返回均使用十进制字符串，按数字格式和数据库类型范围校验；Java 中的 BIGINT 实体字段使用 Long，服务或持久化层完成转换，避免 JavaScript 大整数精度丢失。
  • 新增独立 ID 时，同步维护建表脚本、实体、显式 MyBatis resultMap、查询列、插入语句、接口 DTO、日志和文档；生成和写入日志应记录该 ID，修改语句不得重新生成或覆盖 ID。
  • 修改已存在表的主键或补充必填 ID 前，先确认数据库能力和存量数据，给出保留原记录及其 ID 的迁移方案；Hologres 不支持直接修改主键，不能只修改 CREATE TABLE IF NOT EXISTS 就视为已完成现有表迁移。

API 数值精度规范

  • 对可能超过 JavaScript 安全整数范围（Number.MAX_SAFE_INTEGER）的标识类数值，例如数据库 BIGINT 主键、雪花 ID、任务 ID、订单 ID 等，接口 JSON 必须以字符串输出，禁止直接序列化为 JSON Number。
  • 对外接收上述标识类参数时，DTO 也应使用字符串接收并完成数字格式校验；仅在服务或持久化层转换为 Long，避免前端解析或回传过程发生精度丢失。

输出风格

  • 覆盖范围：问答、代码注释、文档编写等任务
  • 语言习惯：易懂、自然，只保留必要的技术关键词

规范与禁止事项

  • 禁止使用中文引号：除非用户明确要求逐字引用，否则回复中不得出现 Unicode 字符 U+201C 和 U+201D。
  • 禁止翻译腔：避免使用生硬直译、不符合中文母语习惯的词汇（如：接住、击穿、锋利、不崩、不爆、打穿、扛住等）。
    • 【错误示范】：当遇到大流量时，如果缓存被击穿，系统能否扛住压力？如果代码有漏洞，很容易被黑客打穿防线。
    • 【修改后的示范】：当遭遇大流量并发时，若缓存失效导致请求直达数据库，系统能否承受此负载压力？若代码存在安全漏洞，防线极易被黑客攻破。
  • 禁止过度缩减词：避免为了简短而过度简化计算机专业词汇，导致语义丢失或产生歧义。
    • 【错误示范】：服务器出现高负，导致微服响应超时，建议排查连池配置。
    • 【修改后的示范】：服务器出现高负载情况，导致微服务响应超时，建议排查数据库连接池配置。
  • 禁止用中文引号包括的缩减词和短句：尽量减少使用中文引号，避免使用引号来强调非专有名词的缩写词、行业黑话或四字短句。
    • 【错误示范】：这套系统做到了“高可用”，前端实现了“多端适配”，后端进行了“冷热分离”，线程池本身只提供"常驻线程反复取活"的机制。
    • 【修改后的示范】：这套系统具备高可用性，前端实现了多平台适配，后端实现了冷热数据分离存储，线程池本身只提供常驻线程循环取任务的机制。
  • 禁止生造词：避免将英文技术概念生硬糅合，或使用正常技术沟通中不存在的捏造词汇。
    • 【错误示范】：该架构具有极高的高并发抗性，代码的自解释度出色，并展现出良好的容灾力。
    • 【修改后的示范】：该架构能够有效应对高并发冲击，代码可读性强且易于理解，同时具备良好的容灾能力。
  • 禁止滥用“不是……而是……”句式：在没有明确对比、纠错或用户特别要求时，避免使用“不是A，而是B”结构；直接陈述肯定信息通常更简洁、明确，避免将简单判断复杂化。
    • 【错误示范】：该接口响应变慢的原因不是服务器负载过高，而是缓存策略失效。
    • 【修改后的示范】：该接口响应变慢的原因是缓存策略失效
