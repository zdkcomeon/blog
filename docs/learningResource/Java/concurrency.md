## 什么是指令重排序

重排序分为编译重排序和处理器重排序（cpu重排序和内存重排序）

**指令重排序**是指编译器或CPU为了优化程序的执行性能而对指令进行重新排序的一种手段，提高程序的执行效率，减少CPU的等待时间，最大化利用CPU，共有三种指令重排序

编译器重排序：针对程序代码而言，编译器可以在不改变单线程的程序语义和执行结果，进行程序语句的排序

指令重排序：CPU的并行指令集执行，多个指令在执行时，会对那些不存在数据依赖关系的指令进行提前执行，比如初始化赋值这种，避免CPU等待（在执行某一个指令但是这个指令依赖某一个执行，此时CPU处于空闲等待时间，可以利用这个等待时间执行其他指令。最大化利用CPU）

内存重排序：其实就是CPU引入高速缓存后，多个CPU之间的数据不一致，导致的可见行问题，比如，A线程执行修改语句没有及时的刷新数据回到主存，而且其他CPU的高速缓存还是之前的值，不知道主存更新，导致两边数据不一致的问题。内存重排序实际上不是相关的操作被重新排序了，而是因为CPU引入引入缓存，还没有来的及刷新导致的。

## 指令重排序会带来那些问题？为啥要避免指令重排序？

重排序会带来可见性问题，所以在多线程开发中必须要关注并规避重排序。

（可见性，有序性的原因，根源上分析）

内存重排序带来的可见性问题：每个CPU都有自己的缓存，为了提高共享变量的写操作，CPU把整个操作变成异步的了，如果写入操作还没来的及同步到其它CPU，就有可能发生其它CPU读取到的是旧的值，因此看起来这条指令还没执行一样。

指令重排序带来的有序性问题：CPU指令重排序导致的，多线程情况下，不在符合as-if-sercial语义，改变了程序的执行结果，导致了多种可能性的存在。

## ThreadLocal

### 内存泄露

外部对ThreadLocal的强引用消失，在垃圾回收的时候触发了对弱引用的回收，导致ThreadLocal对象被回收了，但是ThreadLocal对应的的value是没有被回收的，一直有这个外部强引用，导致value一直存在，内存泄露。

解决方案：在往map中添加数据或者删除数据时threadLocal都会主动检测发现是否存在key为null的值，主动的释放内存，而且强烈建议使用后，调用remove方法主动释放。

### ThreadLocal为啥设置为虚引用？

目的是为了主动的释放内存，线程的生命周期就是ThreadLocal的生命周期，但是改成弱引用后可以主动的释放内存，如何使用强引用，在我们使用数据后，但是线程生命周期并没有结束，会导致ThreadLocal无法回收，而且还存在线程池，线程复用这种机制。

### 父子线程之间的线程数据共享

·	正常的父子线程之间的数据是不共享的，因为每个线程都有自己的ThreadLocalMap对象，互相不干扰，但创建一个子线程时候，自线程也是拥有自己的一套数据，需要从父线程中copy过来，或者每次查询的时候，检查一下父线程数据。但是Jdk自己提供的有一个父子线程之间数据共享的版本的ThreadLocal，可以使用这个。

## ReentrantLock和synchronized区别？

1. 一个jdk内置的锁，一个基于AQS涉及实现的
2. ReentrantLock 支持多条件，多个阻塞等待队列
3. ReentrantLock支持公平锁
4. ReentrantLock锁等待可释放
5. 二者都是可重入锁，但是lock锁支持非重入锁

## synchronized 和 volatile 有什么区别

1. volatile 本质是告诉 JVM 当前变量在寄存器中的值是不确定的，需要从主存中读
取，synchronized 则是锁定当前变量，只有当前线程可以访问该变量，其他线程被阻
塞住。
2. volatile 仅能用在变量级别，而 synchronized 可以使用在变量、方法、类级别。
3. volatile 仅能实现变量的修改可见性，不能保证原子性；而 synchronized 则可以
保证变量的修改可见性和原子性。
4. volatile 不会造成线程阻塞，synchronized 可能会造成线程阻塞。
5. volatile 标记的变量不会被编译器优化，synchronized 标记的变量可以被编译器
优化

## synchronized锁的升级

无锁 表示没有任何线程持有锁或竞争锁

偏向锁 两个线程CAS竞争锁，存在取不到锁情况，会升级为轻量级锁

轻量级锁 多个线程来回交替获取锁，但是如果一个线程多次CAS获取不到锁，会锁升级为重量级

重量级锁 内核态和用户态之间交替，获取锁，释放锁
