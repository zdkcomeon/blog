Kafka 消费与位移提交

2026/3/23学习资源Kafka消息队列消费者知识梳理大约 13 分钟

整理 poll 参数、自动与手动位移提交、重复消费和消息顺序。

consumer poll 消息频率细节

默认情况下，消费者⼀次会poll500条消息。

//⼀次poll最⼤拉取消息的条数，可以根据消费速度的快慢来设置
props.put(ConsumerConfig.MAX_POLL_RECORDS_CONFIG, 500);

但是为了避免poll拉取的数据一直没有达到max_poll_records，导致一直阻塞等待拉取消息，不处理业务问题，可以在consumer在poll消息的时候，指定一个超时等待时间，即使拉取到的数据不符合要求，但是时间到了也会放弃这轮消息拉取，执行消息消费逻辑。

其实还有两个参数来控制， maxPollSize和minPollSize，以为每次消息的写入和读取都是以record batch 为基本单位的，每个record batch的大小是不固定的，所以poll在拉取消息的时候，一旦发现拉取的消息符合min.pollSIze的时候，会直接放回，对应的数据。当三者都存在的时候，取最小值判断。

演示代码：默认拉取500条数据，而且等待超时时间为1s

  • 如果这⼀次没有poll到500条。且时间在1秒内，那么⻓轮询继续poll，要么到500条，要么到1s
  • 如果多次poll都没达到500条，且1秒时间到了，那么直接执⾏for循环

消息位移提交

位移提交主题

就是将 Consumer 的位移数据作为一条条普通的 Kafka 消息，提交到 consumer_offsets 这个主题中。可以这么说，consumer_offsets 的主要作用是：保存 Kafka 消费者的位移信息，这个提交过程不仅要实现高持久性，还要支持高频的写操作。**consumer_offsets **就是普通的 Kafka 主题，可以手动地创建它、修改它，甚至是删除它。只不过，位移主题同时也是一个内部主题，大部分情况下，你其实并不需要"搭理"它，也不用花心思去管理它，把它丢给 Kafka 就完事了。向位移主题提交的消息 Key 中应该保存 3 部分内容：消费者组ID、主题名、分区名，那个消费者往那个主题的那个分区提交消息。

创建位移提交主题

当 Kafka 集群中的第一个 Consumer 程序启动时，Kafka 会自动创建位移主题。我们说过， 位移主题就是普通的 Kafka 主题，那么它自然也有对应的分区数。但如果是 Kafka 自动创 建的，分区数是怎么设置的呢？这就要看 Broker 端参数 offsets.topic.num.partitions 的 取值了。它的默认值是 50，因此 Kafka 会自动创建一个 50 分区的位移主题。 Broker 端另一个参数 offsets.topic.replication.factor 要做的事情了。它的默认值是 3。 总结一下，如果位移主题是 Kafka 自动创建的，那么该主题的分区数是 50，副本数是 3 ，一个leader副本，2个follower副本。

提交位移主题消息

目前 Kafka Consumer 提交位移的方式有两种：自动提交位移和手动提交位移。

Consumer 端有个参数叫 enable.auto.commit，如果值是 true，则 Consumer 在后台默 默地为你定期提交位移，提交间隔由一个专属的参数 auto.commit.interval.ms 来控制。 自动提交位移有一个显著的优点，就是省事，不用操心位移提交的事情，就能保证消息消 费不会丢失。但这一点同时也是缺点。因为它太省事了，以至于丧失了很大的灵活性和可控 性，你完全没法把控 Consumer 端的位移管理。

手动提交位移，即设置 enable.auto.commit = false。 一旦设置了 false，作为 Consumer 应用开发的你就要承担起位移提交的责任。Kafka Consumer API 为你提供了位移提交的方法，如 consumer.commitSync 等。当调用这些 方法时，Kafka 会向位移主题写入相应的消息 。其实就是位移手动提交，没啥区别。

整理位移主题

选择的是自动提交位移，那么就可能存在一个问题：只要 Consumer 一直启动着， 它就会无限期地向位移主题写入消息。

举个极端一点的例子。假设 Consumer 当前消费到了某个主题的最新一条消息，位 移是 100，之后该主题没有任何新消息产生，故 Consumer 无消息可消费了，所以位移永 远保持在 100。由于是自动提交位移，位移主题中会不停地写入位移 =100 的消息。显然 Kafka 只需要保留这类消息中的最新一条就可以了，之前的消息都是可以删除的。这就要求 Kafka 必须要有针对位移主题消息特点的消息删除策略，否则这种消息会越来越多，最终撑爆整个磁盘 。但是手动提交位移就不有这个问题，自动提交位移，会间隔一段时间提交一次，大量重复数据，但是手动只有拉取到消息，才会触发提交。

** Kafka 使用Compact 策略来删除位移主题中的过期消息，避免该主题无限 期膨胀。那么应该如何定义 Compact 策略中的过期呢？对于同一个 Key 的两条消息 M1 和 M2，如果 M1 的发送时间早于 M2，那么 M1 就是过期消息。Compact 的过程就是扫 描日志的所有消息，剔除那些过期的消息，然后把剩下的消息整理在一起。（参考一下redis的AOF文件重写机制，直接内存快照，写入最新数据）。就是消息Kafka的消息整理机制，compress messages。**

** Kafka 提供了专门的后台线程定期地巡检待 Compact 的主题，看看是否存在满足条件的 可删除数据。这个后台线程叫 Log Cleaner。 **

自动提交消息位移

自动提交位移开启

Consumer 端有个参数 enable.auto.commit，把它设置 为 true 或者压根不设置它就可以了。因为它的默认值就是 true，即 Java Consumer 默认 就是自动提交位移的。如果启用了自动提交，Consumer 端还有个参数就派上用场了： auto.commit.interval.ms。它的默认值是 5 秒，表明 Kafka 每 5 秒会为你自动提交一次 位移 。

提交频率指的是：最小的提交间隔。比如默认值是 5s，那么 Kafka 保证的是至少等待 5s 才会自动提交一次，

  • 不可能出现 3s 时提交的情况；
  • 但是可能出现由于 5s 时消息还没有处理完，仍在执行业务代码，那么只有处理完消息后，后续再一次执行 poll 时才会自动提交消费位移的情况，此时自动提交的时间间隔超过 5 s。

自动提交消费位移的代码逻辑是在 KafkaConsumer#poll() 里实现的，

  • 如果时间间隔 ＞ 最小提交间隔，就会进行 offset 提交逻辑
  • 如果时间间隔 ＜ 最小提交间隔，则忽略 offset 提交逻辑，等待下一次执行 poll 再检查时间间隔判断是否执行自动提交消费位移的代码逻辑

上次 poll 的数据即便处理结束，没有调用下一次 poll，那么也不会进行自动提交消费位移。

自动提交带来的消息重复消费

在默认情况下，Consumer 每 5 秒自动提交一次位移。现在，我们假设提交位移之后的 3 秒发生了 Rebalance 操作（自动提交是提交offset，再处理数据，这时候已经处理3s的数据，但是没有提交offset）。在 Rebalance 之后，所有 Consumer 从上一次提交的位移处继续消费，但该位移已经是 3 秒前的位移数据了，故在 Rebalance 发生前 3 秒消费的所有数据都要重新再消费一次。（上次 poll 的数据即便处理结束，没有调用下一次 poll，那么也不会进行自动提交消费位移。）虽然可以能够通过减少 auto.commit.interval.ms 的值来提高提交频率，但这么做只能缩小重复消费的时间窗口，不可能完全消除它。这是自动提交机制的一个缺陷。

手动提交位移

** enable.auto.commit 为 false ，显示的调用位移提交API，commitAsync or commitSync**

commitSync

该方法会提交 KafkaConsumer#poll() 返回的最新位移。它是一个同步操作，即该方法会 一直等待，直到位移被成功提交才会返回。如果提交过程中出现异常，该方法会将异常信息抛出。 调用 consumer.commitSync() 方法的时机，是在你处理完了 poll() 方法返回的所 有消息之后。 （一旦咱们过早提交调用了，会导致消息没有消费完，就提交offset了）。此外commitSysnc是一个同步阻塞的操作， Consumer 程序会处于阻塞状态， 直到远端的 Broker 返回提交结果，这个状态才会结束。

commitAsync

调用 commitSync() 时，Consumer 程序会处于阻塞状态， 直到远端的 Broker 返回提交结果，这个状态才会结束 。

鉴于这个问题，Kafka 社区为手动提交位移提供了另一个 API 方法： KafkaConsumer#commitAsync()。

commitAsync是异步的，那如果还没有提交消费位移，就 poll 拉取了下一批，为什么不会拉取到重复消息呢？

commitAsync不会拉取到重复消息，即使不 commit，循环执行 poll 也不会拉取到重复消息。 只要 Consumer 没有重启，就不会发生重复消费。 如果 Consumer 重启了，那么它首先会从位移主题 __consumer_offsets 获取消费位移的位置；之后 Consumer 会维护一个消费位移（和位移主题中的消费位移不同，consumer自身维护的），在 poll 的过程中不断更新；Consumer 在发送拉取消息请求的时候告诉 Broker 它想要的消息的消息起始位移（把它维护的消费位移发送给 Broker）。

注

从这里也可以看到，__consumer_offsets位移主题，存在记录持久化消费者的消费位移，即使consumer宕机重启也会从最新上一次提交位移的位置拉取消息，避免消费者重启了，不知道从哪消费，导致的消费重复，异常问题。

而且comsumer每次poll消息也会提交自己要拉取的数据offset，从哪里开始，所以即使commitAsync是异步的提交，但是咱们poll的数据是最新的，但是这个过程中，一旦commitAsync失败，而且消费者重启，就会导致重复消费问题。

使用 KafkaConsumer#commitsync() 或者 commitAsync() 提交的消费位移主要是为了：****保证 Consumer 重启之后恢复消费进度，保证可靠性。

commitAsync 能否替代 commitSync

当然不能，commitAsync 的问题在于，出现问题时 commitAsync 不会自动重试。因为它是异步操作，倘若提交失败后自动重试，那么它重试时提交的位移值可能早已经"过期"或不是最新值了（可能出现新值被旧值覆盖的情况）。因此，异步提交的重试其实没有意义，所以commitAsync 是不会重试的。

commitAsync 和 commitSync组合使用

使用二者有点，个取所长，对于常规性、阶段性的手动提 交，调用 commitAsync() 避免程序阻塞，而在 Consumer 要关闭前，我们调用 commitSync() 方法执行同步阻塞式的位移提交，以确保 Consumer 关闭前能够保存正确 的位移数据。

更加细粒度化地提交位移

实际上，Kafka Consumer API 还提供了一组更为方便的方法，可以帮助你实现更精细化的位移管理功能。刚刚我们聊到的所有位移提交，都是提交 poll 方法返回的所有消息的位移，比如 poll 方法一次返回了 500 条消息，当你处理完这 500 条消息之后，前面我们提到的各种方法会一次性地将这 500 条消息的位移一并处理。简单来说，就是直接提交最新一条消息的位移。但如果我想更加细粒度化地提交位移，该怎么办呢？

设想这样一个场景：你的 poll 方法返回的不是 500 条消息，而是 5000 条。那么，你肯定不想把这 5000 条消息都处理完之后再提交位移，因为一旦中间出现差错，之前处理的全部都要重来一遍（比如consumer宕机重启，从消费位移里面记得是上次提交的值）。这类似于我们数据库中的事务处理。很多时候，我们希望将一个大事务分割成若干个小事务分别提交，这能够有效减少错误恢复的时间。 在 Kafka 中也是相同的道理。对于一次要处理很多消息的 Consumer 而言，它会关心社区有没有方法允许它在消费的中间进行位移提交。比如前面这个 5000 条消息的例子，你可能希望每处理完 100 条消息就提交一次位移，这样能够避免大批量的消息重新消费。

** Kafka Consumer API 为手动提交提供了这样的方法： commitSync(Map) 和 commitAsync(Map)。它们的参数是一个 Map 对象，键就是 TopicPartition，即消费的分区，而值是一个 OffsetAndMetadata 对象， 保存的主要是位移数据。 提交那个分区的offset值。**

Kafka消费者如何保证不重复消费

首先生产者不重复发送消息，消费者需要采用额外的手段控制不重复消费，比如通过消息的key来判断，采用布隆过滤器，本地消息表等，此外还要保证提交的offset的值是正确的。

如何保证消息的有序发送和有序消费

只能保证单分区的有序存储发送，多分区是没法控制的，要实现多分区的有序消费，是需要加入额外的手段进行控制。

消费拉取消息的频率控制

Kafka采用长轮询poll消息，默认情况下，消费者⼀次会poll500条消息，当然这个MAX_POLL_RECORDS_CONFIG参数可根据实际业务配置合理的参数。

//⼀次poll最⼤拉取消息的条数，可以根据消费速度的快慢来设置 props.put(ConsumerConfig.MAX_POLL_RECORDS_CONFIG,500);

poll消息时候，指定了⻓轮询的时间，即默认拉取消息默认等待的时间，存在下面三种情况：分别是数据拉取量符合了，或者时间到了

  • 如果⼀次poll到500条，就直接执⾏for循环
  • 如果这⼀次没有poll到500条。且时间在1秒内，那么⻓轮询继续poll，要么到500条，要么到1s
  • 如果多次poll都没达到500条，且1秒时间到了，那么直接执⾏for循环
