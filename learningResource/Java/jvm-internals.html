JVM 运行机制与对象布局

2026/10/10学习资源JavaJVM对象布局垃圾回收类加载字节码知识梳理大约 20 分钟

围绕一个 Java 对象从创建、访问到回收的过程，整理 JVM 内存、方法调用和类加载机制。

JVM 运行时内存区域

线程私有的区域

区域主要作用
程序计数器保存当前线程正在执行的 JVM 指令地址，参与分支、循环、异常处理和线程切换后的执行恢复。执行本地方法时，其值在规范中是未定义的。
Java 虚拟机栈保存方法调用对应的栈帧，生命周期与线程一致。
本地方法栈为 native 方法的执行提供支持，具体组织方式由 JVM 实现决定。

每次方法调用会创建一个栈帧，正常返回或异常退出时销毁。栈帧主要包含局部变量表、操作数栈、动态链接所需信息，以及返回和异常处理相关信息。

局部变量可以保存基本类型的值和对象引用；对象引用所指向的对象通常分配在堆中。区域划分和栈帧语义见 JVM 规范第 2 章。

线程共享的区域

堆

堆用于分配对象和数组，是垃圾回收的主要管理区域。

  • -Xms：设置初始堆大小。
  • -Xmx：设置最大堆大小。

方法区与元空间

方法区是 JVM 规范中的逻辑区域，保存类的结构、字段与方法信息、运行时常量池等内容。

在 HotSpot 中，JDK 8 起使用本地内存中的元空间存储类元数据。方法区的逻辑定义与元空间的物理实现需要分开理解：静态引用字段所引用的对象仍位于堆中，即时编译产生的机器码则由代码缓存管理。

元空间和压缩类指针的实现说明见 HotSpot 类元数据。

运行时常量池

运行时常量池属于方法区，每个类或接口都有自己的运行时常量池。它由 Class 文件中的常量池构建，包含常量以及类、字段、方法等符号引用。

符号引用在解析时与实际的类、字段或方法建立联系。运行时常量池和保存字符串对象的堆空间具有不同职责。

Java 对象的创建过程

以执行 new 创建普通对象为例，可以按以下过程理解：

  1. 确认类已就绪：检查目标类是否已经加载、链接和初始化，必要时触发相应过程。
  2. 分配对象内存：根据类的布局确定所需空间，从堆中分配。
  3. 进行零值初始化：将实例字段设为默认值，例如整数为 0、布尔值为 false、引用为 null。
  4. 设置对象头：写入类型指针、初始状态等信息。身份哈希码通常按需计算，并不要求在创建时生成。
  5. 执行实例初始化：调用构造器对应的 <init>，完成父类构造、实例字段初始化和构造器逻辑。
  6. 使用或发布对象引用：调用方取得对象引用，继续访问对象。

这里描述的是理解对象创建的逻辑过程，具体实现可以在保持 Java 语义的前提下优化。

内存分配方式

方式适用情形与含义
指针碰撞可用空间较规整时，移动分配指针即可划出对象所需的区域。
空闲列表空闲空间不连续时，维护可用内存块，从中选择足够大的区域。
线程本地分配缓冲区（TLAB）为线程预留一小块堆空间，线程优先在自己的区域内分配，减少共享分配指针上的竞争。

TLAB 是分配优化，仍属于堆空间。多个线程竞争共享分配区域时，HotSpot 可以使用 CAS 等方式保证分配操作的正确性。

对象初始化与安全发布

零值初始化保证字段具有默认值，构造器负责设置业务所需的初始状态。将对象引用写入共享变量时，还需要保证安全发布。

缺少必要的同步关系时，其他线程可能看到尚未完全初始化的状态。应根据场景使用 volatile、锁、类初始化等机制建立可见性与顺序保证，不能仅凭源代码中的赋值顺序判断其他线程的观察结果。

Java 对象的内存布局

下面的大小示例以 64 位 HotSpot、传统对象头、8 字节对象对齐 为前提。压缩配置、JDK 版本、字段布局和对象对齐参数都会影响结果；启用紧凑对象头后，需要重新分析布局。

对象头

传统对象头主要包含以下信息：

部分作用示例中的大小
Mark Word编码身份哈希码、分代年龄和锁状态等信息，具体含义随对象状态与 JVM 实现变化。8 字节
类型指针指向对象所属类的元数据。未压缩时 8 字节，压缩时 4 字节
数组长度记录数组元素数量，仅数组对象具有此项。4 字节

Mark Word 会在不同状态下复用位空间，并不是所有信息都一直同时保存在其中。历史 HotSpot 实现还包含偏向锁相关编码，分析具体位布局时应核对目标 JDK，不能沿用一个固定版本的图示。

类型指针属于对象头中的独立部分，不应混入 Mark Word 的大小计算。

实例数据与对齐填充

实例数据包括本类和父类的实例字段。基本类型字段保存对应的值，引用类型字段保存对象引用。引用指向的对象有自己的内存空间，不会直接计入当前对象的浅大小。

在这里使用的 8 字节对齐配置下，对象总大小需要向上补齐到 8 的倍数。对象头本身可以是 12 字节，并不要求对象头单独满足 8 字节对齐。

两个压缩选项分别影响不同内容：

  • UseCompressedClassPointers：影响对象头中的类型指针。
  • UseCompressedOops：影响堆中普通对象引用，例如引用类型实例字段。

两者应分别确认。相关参数见 HotSpot 压缩指针说明 和 Java 命令中的对象对齐与紧凑对象头选项。

空对象与空数组的大小

Object object = new Object();
int[] numbers = new int[0];

以下只计算对象本身，不包含局部变量 object、numbers 所占的引用存储空间。

对象未压缩类型指针压缩类型指针
new Object()8 + 8 = 16 字节8 + 4 = 12 字节，补齐后 16 字节
new int[0]8 + 8 + 4 = 20 字节，补齐后 24 字节8 + 4 + 4 = 16 字节

空数组虽然没有元素数据，仍然需要保存对象头和数组长度。

包含实例字段的对象

class A {
    String name;
    Object obj;
    int a;
    float f;
}

在没有继承实例字段、没有额外字段填充的情况下，按上述配置计算：

配置对象头实例字段对齐后的总大小
不压缩类型指针和普通对象引用8 + 8 = 168 + 8 + 4 + 4 = 2416 + 24 = 40 字节
同时压缩类型指针和普通对象引用8 + 4 = 124 + 4 + 4 + 4 = 1612 + 16 = 28，补齐后 32 字节

未压缩时，对象头与实例字段相加得到 40 字节，已经满足 8 字节对齐。引用字段为 null 时仍然占用引用槽位；name 和 obj 指向的其他对象需要另外计算。

如果类中只有 String name 和 Object obj 两个引用字段，在相同前提下，不压缩时为 16 + 8 + 8 = 32 字节，同时压缩时为 12 + 4 + 4 = 20 字节，补齐后为 24 字节。

对象引用如何定位对象

方式访问过程特点
句柄访问引用先指向句柄，再通过句柄找到实例数据或类型信息。对象移动后，可以更新句柄中的地址。
直接访问引用直接定位对象，对象头提供访问类型元数据所需的信息。减少一次间接访问；对象移动时需要处理相关引用。

HotSpot 通常采用直接访问。JVM 规范没有要求所有虚拟机使用相同的对象表示方式。

垃圾回收

理解垃圾回收时，可以先回答三个问题：哪些区域需要回收、对象何时可回收、采用什么方式回收。

堆是主要回收区域，类卸载时也可能释放对应的类元数据。栈帧则随着方法退出销毁，其生命周期管理与堆中的对象回收不同。

如何判断对象是否可回收

引用计数法为对象维护引用数量，引用增加或减少时更新计数。它便于理解，但单纯的引用计数无法处理对象之间的循环引用。

可达性分析从 GC Roots 出发遍历对象引用关系。无法从这些起点到达的对象，才可能进入后续回收流程。

复习 GC Roots 时，可以重点关注：

  • 活跃线程栈帧中的对象引用。
  • JNI 持有的相关引用。
  • 仍存活的类所持有的静态引用，以及类与运行时常量池相关的存活引用关系。
  • 活动线程对象、虚拟机内部结构等持有的引用。

可达性分析不仅要判断对象之间是否互相引用，还要判断整个引用关系是否能从 GC Roots 到达。

强、软、弱、虚引用

引用类型含义
强引用对象仍可从 GC Roots 通过强引用到达时，会保持存活。
软引用可用于对内存敏感的缓存；垃圾回收器会在内存需求等因素下决定是否清除。
弱引用对象被判定为仅弱可达时，相关弱引用会被清除。
虚引用用于在对象到达相应回收状态时配合引用队列进行通知与清理，get() 始终返回 null。

单次执行 System.gc() 并不保证立即观察到某个对象被回收。

finalize 与对象是否已死

历史上的 finalize() 机制允许对象在符合条件时进入终结处理流程，并可能通过重新建立可达引用使对象恢复可达。对同一个对象，虚拟机不会自动重复调用其 finalize()。

终结处理是否执行、何时执行都不能作为业务逻辑的可靠保证，不能把对象回收理解成每次固定执行两轮 GC。

finalize() 已被标记为弃用并计划移除。资源管理应优先使用 AutoCloseable 和 try-with-resources，具体语义见 Object.finalize 文档。

分代布局

传统分代模型将堆划分为新生代和老年代。新生代可以进一步划分为 Eden、Survivor From 和 Survivor To。

新生代约占堆的 1/3、老年代约占 2/3，以及 Eden 与两个 Survivor 的 8:1:1，可以作为一种配置示例。实际比例取决于收集器、参数与运行状态，不能作为所有 JVM 的固定布局。

G1 使用 Region 组织堆空间，新生代和老年代的 Region 集合可以动态调整。

垃圾回收算法

算法基本过程优点主要代价与常见场景
标记-清除标记存活对象，清除可回收对象占用的空间。不必移动所有存活对象。可能产生内存碎片，CMS 曾采用这一思路管理老年代。
标记-复制将存活对象复制到目标区域，再释放原区域。复制后空间较规整，分配方便。需要保留目标空间，复制成本受存活对象数量影响，常用于新生代。
标记-整理标记存活对象后移动对象，集中可用空间。减少内存碎片。移动对象和更新引用存在成本，常用于老年代。

分代收集是按不同年龄对象的存活特征组合回收策略，而不是要求所有区域都使用同一种算法。

常见垃圾回收器

收集器主要特征
Serial / Serial Old分别用于新生代和老年代的单线程收集器，回收期间需要暂停应用线程。
ParNew新生代并行收集器，可理解为 Serial 的多线程版本，属于历史收集器组合中的常见成员。
Parallel Scavenge / Parallel Old关注吞吐量的新生代和老年代并行收集器。
CMS采用并发标记清除思路的历史老年代收集器，仍存在暂停阶段和碎片问题。
G1按 Region 组织堆，结合并发标记和存活对象转移管理新生代、老年代。

CMS 已在 JDK 14 中移除，阅读旧版本调优资料时需要核对目标 JDK 的可用收集器，见 JDK 迁移指南中的已移除组件。

JVM 如何实现方法调用

五种方法调用指令

指令主要用途
invokestatic调用静态方法。
invokespecial用于构造器、父类方法等需要特殊选择规则的实例方法调用，也用于相应的私有方法、接口默认方法调用场景。
invokevirtual常见的类实例方法调用，可根据实际接收者类型进行动态分派。
invokeinterface面向接口的方法调用，根据实际接收者选择实现。
invokedynamic链接动态调用点，由引导方法建立调用点与目标的关系。

分析方法调用时，需要区分类实例调用、接口调用和动态调用，再结合方法属性理解具体的分派过程。

虚方法、静态绑定与动态绑定

虚方法通常指可以通过重写参与动态分派的实例方法。静态方法、私有方法、final 方法和构造器不参与基于子类重写的动态分派。

静态绑定的调用目标不需要根据接收者的运行时类型选择，例如静态方法调用。符号引用解析后，会建立到相应目标的联系。

动态绑定需要根据对象的实际类型选择实现。例如父类引用指向子类对象时，调用被子类重写的方法会选择子类实现。

invokevirtual 也可能用于无法重写的 final 实例方法，因此判断是否发生动态分派时，还要结合方法属性和运行时优化。

虚方法表与接口方法表

在常见 HotSpot 实现中，可以通过虚方法表（vtable）理解类实例方法的分派：

  1. 方法表保存参与分派的方法信息，包括继承的方法。
  2. 子类重写父类方法时，复用相应表项的位置。
  3. 调用时取得接收者的实际类型，再根据相应表项找到目标方法。

表项可以包含具体实现或抽象方法相关信息。

接口调用还需要处理接口与具体实现之间的对应关系，可以结合接口方法表（itable）理解。

相较于直接定位已确定的目标，方法表分派增加了类型和表项的访问。即时编译器可以进一步进行内联、去虚化等优化，实际执行成本需要结合具体调用点分析。

方法表的组织方式属于实现细节，方法解析与选择的规范见 JVM 规范中的解析和方法选择。

类加载与初始化

类的生命周期

类的生命周期可以按以下阶段理解：

  1. 加载：获取类的二进制表示，创建运行时的类结构。
  2. 链接：包括验证、准备和解析。
  3. 初始化：执行规范规定的初始化流程，以及需要执行的 <clinit>。
  4. 使用：创建实例、调用方法、访问字段等。
  5. 卸载：满足条件时，释放类及其元数据。

链接的三个阶段

阶段主要工作
验证检查 Class 文件格式、字节码类型安全、成员访问等约束。
准备创建静态字段的存储并设置默认值，例如 0、false、null。
解析将运行时常量池中的符号引用解析为实际的类、字段或方法等目标。

解析可以按需进行。解析某个符号引用可能触发相关类的加载，但不一定同时触发该类初始化。

编译期常量可以通过 ConstantValue 表示，在规范规定的初始化流程中取得相应常量值。普通静态字段的显式赋值和静态代码块由 <clinit> 执行；仅有 static final 修饰并不意味着它一定是编译期常量。

初始化方法

编译器收集需要执行的静态字段赋值和静态代码块，生成类或接口初始化方法 <clinit>。实例构造对应的是 <init>，两者承担不同职责。

例如，静态字段首先具有默认值，随后在类初始化过程中执行相应赋值逻辑。类初始化需要保证线程安全，同一运行时类的成功初始化只执行一次。

什么情况下触发初始化

需要把加载和初始化分开理解。加载可以提前发生，常见的初始化触发情形包括：

  • 执行 new 创建该类实例。
  • 访问需要初始化的静态字段，或调用静态方法；具体初始化的是声明相应字段或方法的类型。
  • 通过特定反射操作使用该类。
  • 初始化子类时，先初始化其父类。
  • 初始化实现类时，初始化相关的、声明默认方法的父接口。
  • JVM 启动时指定初始类或接口。
  • 首次调用解析得到的特定 MethodHandle，其种类涉及静态字段访问、静态方法调用或构造器调用。

编译期常量可能被编译进使用者的 Class 文件，单纯读取这种常量不一定触发声明类的初始化。完整规则见 JVM 规范中的初始化。

双亲委派机制

常见类加载器在接到加载请求时，先检查是否已经加载，再按委派策略请父加载器处理；父加载器无法处理时，才尝试自行加载。

这种方式有助于基础类型由共同的加载器加载，减少同名类型的不一致。它是一种类加载器设计模式，具体加载器可以按隔离、容器或模块需求实现不同策略。

进一步的类加载器、类隔离和热部署笔记见 JVM 类加载与字节码。

类初始化为什么可能死锁

类初始化有同步保护。如果线程一正在初始化类 A，过程中等待类 B 初始化完成，而线程二正在初始化类 B，过程中又等待类 A 初始化完成，就可能形成循环等待。

这类问题常见于静态字段初始化或静态代码块中的相互依赖。排查时应结合线程栈确认当前线程正在初始化哪个类、正在等待哪个类，并减少初始化阶段的跨类循环依赖。

Class 文件、Lambda 与 invokedynamic

Class 文件中的常量池保存方法、字段和类型等符号信息，方法的 Code 属性保存字节码。分析动态调用时，还需要结合 BootstrapMethods 属性中的引导方法信息。

可以通过以下命令查看字节码和常量池：

javap -c -v Demo.class

Lambda 调用的基本过程

Runnable task = () -> System.out.println("hello");
task.run();

常见 javac 编译结果可以按以下过程理解：

  1. Lambda 表达式所在位置生成一个 invokedynamic 调用点。
  2. 常量池中的 CONSTANT_InvokeDynamic 信息关联引导方法索引和调用点的名称、类型。
  3. BootstrapMethods 指向相应引导方法，Lambda 常见的是 LambdaMetafactory.metafactory() 或其变体。
  4. 引导方法建立并返回 CallSite，其目标通过 MethodHandle 描述可执行的调用行为。
  5. 已链接的调用点用于创建或获取函数式接口实例，并按需要捕获变量。
  6. 调用接口方法时，执行对应的 Lambda 实现逻辑。

CallSite 表示动态调用点，MethodHandle 是带有方法类型的可执行句柄，可以表示方法、构造器或字段访问。

函数式接口由表达式上下文决定，例如 Runnable、Supplier 或 Function。是否分配新的接口实例、是否复用已有实例，取决于捕获情况和运行时实现。链接、捕获与调用的区别见 LambdaMetafactory 文档。

Stream 与 Lambda 的关系

Stream 管道通过普通方法和接口调用组织操作，作为参数传入的 Lambda 可以使用上述动态调用机制构造。分析字节码时，应分别观察 Lambda 实例的创建、接口方法调用以及 Stream 自身的方法调用。

内存溢出与内存泄漏

概念含义常见表现
内存溢出（Out of Memory）某次内存需求无法满足，JVM 抛出 OutOfMemoryError。堆无法分配对象、元空间不足，或无法为新线程分配所需资源等。
内存泄漏（Memory Leak）对象已经不再被业务使用，却仍被引用关系保留，导致相关内存长期无法回收。未限制大小的缓存、未注销的监听器、长期保留对象的集合等。

内存泄漏持续累积可能造成内存溢出，内存需求本身过大或配置不足也可能直接造成内存溢出。

将超出 int 范围的数值放入整数运算中涉及数值溢出或类型转换规则。递归过深等情况可能导致 StackOverflowError。这些问题应分别分析。

Java 堆对象由垃圾回收器管理。排查泄漏时，重点是找到不再需要的对象仍然被谁引用，以及这些引用为何没有及时解除。
